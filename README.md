# 督学交付质量监控

每天自动扫一遍几百个督学服务群的聊天记录，按预设规则判定当天服务有没有做到位，
产出每群「完成 / 未完成 + 缺失项」，并把未完成清单推给主管。

面向的是这样一个场景：机构有 400 到 500 个外部群，群里是家长和学生，
所以不能挂群机器人；督学老师每天要发学科计划、学生要打卡，
主管靠人工翻群根本核不过来。

> ⚠️ 仓库只含代码和规则配置。学员名册、判定结果、聊天记录都属于业务数据，一概不在仓库里。

## 判定逻辑

规则全部写在 `rules.yaml`，改标签不用动代码：

```yaml
checkin_tag: "#今日打卡"
plan_tag_template: "#{subject}今日计划"
```

每天对每个学生扫两件事。群里当天有没有出现打卡标签，以及学生报的每一门科目
是不是都出现了对应的计划标签。`{subject}` 会按学生科目逐个展开，
所以报了「行测 + 申论」的学生，两科计划缺一科就算未完成。

学生名单从主管导出的 xlsx 读入，多 sheet 结构，按服务起止日期过滤当天在服务的人。

## 两种取数方案

同一套判定逻辑，两条拿聊天记录的路径。根目录是方案 B，`会话存档方案/` 是方案 A。

| | 方案 A · 官方会话存档 | 方案 B · 客户端自动化 |
|---|---|---|
| 目录 | `会话存档方案/` | 仓库根目录 |
| 取数 | 企微官方存档 SDK 拉密文，本地 RSA 解密 | 驱动已登录的企微客户端逐群读 |
| 前提 | 需采购存档许可，走法务流程 | 无采购，本人需在所有群里 |
| 部署 | Docker + APScheduler | 客户机常驻脚本 |
| 数据 | 完整、合规、可扩展 | 够用，但依赖客户端 UI |

方案 B 又分两条 reader，用 `READER` 环境变量切换。`mcp` 走 wecom-cli 的 MCP 授权调 API，
不依赖界面，是默认；`rpa` 走 macOS Accessibility API 读客户端界面，作兜底。

`技术方案.md` 里有完整的选型对比，包含第三条被否掉的路径和各自的成本估算。

## 跑起来

```bash
pip install -r requirements.txt
cp .env.example .env
USE_MOCK=true python3 main.py
```

`USE_MOCK=true` 用 `mock_data.py` 里几组典型状态跑通链路，不碰企微，
覆盖「完整完成」「缺打卡」「缺一科计划」「完全没动作」四种情况。

真跑需要把名册 xlsx 放到 `ROSTER_XLSX` 指的位置，然后：

```bash
USE_MOCK=false python3 main.py
```

带日期参数可以回溯某天：`python3 main.py 2026-07-26`。

## 输出

`data/students.csv` 是学生主表，按编号 upsert，记录首见和末见时间。
`data/checks.csv` 是每日判定历史，一行一个学生一天，含状态、缺失项和命中证据原文。
超过 `RETENTION_DAYS` 天的记录自动清理，默认 7 天。

未完成清单会按 markdown 推到 `WECOM_BOT_WEBHOOK` 指的内部管理群。这个群是内部群，可以挂机器人。

## 部署

`workbuddy指令.md` 是两段可以直接粘给 workbuddy 的任务描述，一段配定时调度，一段配取数。
方案 A 目录下有 `Dockerfile` 和 `docker-compose.yml`。
